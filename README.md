# CommonLib

**CommonLib** — набор повторно используемых библиотек .NET для разработки приложений и расширений. Репозиторий объединяет общие контракты, инфраструктурные реализации, сервисы, средства логирования, настройки, обновления и адаптеры для CAD-платформы.

Основная задача решения — выносить типовую функциональность из отдельных продуктов в независимые компоненты, чтобы подключать их в других решениях без копирования исходного кода. Проекты библиотеки разделены по ответственности: контракты не зависят от реализаций, общая инфраструктура не привязана к конкретному продукту, а интеграция с nanoCAD вынесена в отдельные модули.

Проект **NC** в составе решения — демонстрационный пример приложения-потребителя библиотек CommonLib. Он показывает один из вариантов их совместного подключения и инициализации, но не является назначением всего репозитория.

## Состав решения

### Библиотеки

| Проект | Назначение |
| --- | --- |
| **Abstractions** | Общие интерфейсы, контракты сервисов, настройки, логирование и инфраструктурные типы. Базовый слой, от которого зависят реализации и потребители. |
| **Infrastructure** | Общие реализации инфраструктурных сервисов: сведения об аддоне, CAD-хосте и системе, реестр сведений о сборках, пользовательские сообщения и оконные диалоги. |
| **Infrastructure.NC** | Адаптеры инфраструктурных контрактов для nanoCAD: работа с активным документом, главным окном и выводом сообщений средствами CAD-хоста. |
| **Common.NC** | Повторно используемые команды nanoCAD, контекст сервисов аддона и вспомогательные CAD-классы. Включает команды управления настройками, логированием и обновлениями. |
| **MulticadInterop** | Reflection-обёртки над API MultiCAD. Позволяет обращаться к поддерживаемым API без compile-time ссылки на конкретную версию SDK. |
| **LogBootstrap** | Программная настройка NLog и предоставление абстракций логирования через `IDrzLoggerFactory` и `IDrzLogger`. |
| **Settings** | Хранение и управление настройками аддона на основе контрактов из `Abstractions`. |
| **Updater** | Проверка, загрузка и установка обновлений, проверка целостности пакетов, резервирование файлов и обработка отката. |
| **AddOnRuntime** | Сборка инфраструктуры аддона: composition root, регистрация реализаций и создание сервисов приложения. Использует Simple Injector. |

Подробности публичных возможностей и ограничений конкретных библиотек приведены в README соответствующих проектов.

## Архитектура

Компоненты разделены по слоям и границам ответственности:

```text
                         Приложение / аддон
                                  |
                    +-------------+-------------+
                    |                           |
                AddOnRuntime                  Common.NC
                    |                           |
        +-----------+-----------+               |
        |           |           |               |
   Infrastructure  Infrastructure.NC        Updater
        |           |                           |
        +-----------+---------------------------+
                    |
                Abstractions

   Отдельные функциональные библиотеки:
   +----------------+  +------------+  +----------------+
   |  LogBootstrap  |  |  Settings  |  | MulticadInterop |
   +----------------+  +------------+  +----------------+
```

Схема показывает логические роли компонентов, а не полный граф ссылок между проектами. Фактические зависимости задаются в файлах `.csproj`.

Основные архитектурные принципы:

- **Abstractions отделён от реализаций.** Потребители используют интерфейсы и контракты, а конкретные реализации подключаются на уровне приложения.
- **Инфраструктура отделена от прикладного кода.** Работа с файловой системой, сведениями о системе, окнами и CAD API сосредоточена в специализированных проектах.
- **Интеграция с хостом изолирована.** Код, зависящий от nanoCAD, размещается в `Infrastructure.NC` и `Common.NC`; общие компоненты не должны получать лишнюю зависимость от SDK хоста.
- **Композиция выполняется на границе приложения.** `AddOnRuntime` собирает необходимые реализации и сервисы. Конкретное приложение отвечает за вызов инициализации в своей точке входа.
- **Функциональные модули можно подключать отдельно.** Необязательно использовать весь набор CommonLib: состав ссылок определяется задачами конкретного приложения и транзитивными зависимостями выбранных проектов.

## Использование библиотек в другом решении

Библиотеки CommonLib предназначены для повторного использования в других .NET-решениях.

Рекомендуемый порядок подключения:

1. Выбрать только необходимые модули и определить их транзитивные зависимости по файлам проектов.
2. Добавить выбранные проекты в решение как ссылки на проекты (`ProjectReference`) либо использовать собранные библиотеки в принятом в продукте формате поставки.
3. Подключить контракты из `Abstractions` и использовать их в коде потребителя.
4. Реализовать или подключить требуемые инфраструктурные сервисы.
5. Зарегистрировать реализации в точке композиции приложения. Для сценария аддона можно использовать `AddOnRuntime`.
6. Если используются общие команды `Common.NC`, инициализировать `AddOnContext` до вызова этих команд и обеспечить наличие необходимых сервисов.
7. Для CAD-интеграции подключать только соответствующие адаптеры и SDK целевого хоста.

Не следует копировать реализации из CommonLib в проект-потребитель или обращаться к конкретным инфраструктурным классам там, где достаточно интерфейса из `Abstractions`.

## Требования и технологии

Параметры различаются в зависимости от модуля:

- `Abstractions` и `MulticadInterop` ориентированы на `.NET Standard 2.0`.
- Большинство остальных библиотек и демонстрационных проектов используют `.NET 6` и `net6.0-windows`.
- CAD-модули используют API nanoCAD; для их сборки и выполнения необходимы соответствующие пакеты SDK и совместимая среда.
- `LogBootstrap` использует NLog через пакет `drzNLog`.
- `Updater` использует `drzSharpSevenZip`.
- `AddOnRuntime` использует Simple Injector для композиции сервисов.

Конкретные версии пакетов и целевые платформы указаны в соответствующих `.csproj`.

## Сборка решения

Для сборки требуется Windows-среда с установленным .NET SDK, поддерживающим используемые целевые платформы, а также доступ к NuGet-источникам зависимостей.

1. Открыть `CommonLib.sln` в Visual Studio или перейти в каталог решения в терминале.
2. Восстановить NuGet-пакеты.
3. Собрать нужную конфигурацию.

Пример команд:

```powershell
dotnet restore .\CommonLib.sln
dotnet build .\CommonLib.sln -c Debug
```

Для сборки отдельных библиотек можно указать соответствующий `.csproj` вместо файла решения. Для модулей nanoCAD может потребоваться установленная/доступная среда и пакеты CAD SDK.

### Общие параметры MSBuild

Каждый проект CommonLib явно импортирует файлы с именем, зависящим от свойства `$(SolutionName)`:

- `$(SolutionName).Build.props` — общие свойства сборки;
- `$(SolutionName).Build.targets` — общие цели сборки.

Путь в `Import` задан относительно каталога самого файла проекта. В текущей структуре CommonLib это каталог репозитория. Импорт условный: файл подключается только в том случае, если он существует.

Это поведение намеренное и позволяет использовать одни и те же проекты в разных решениях, не применяя настройки CommonLib к стороннему продукту:

- При сборке самого решения CommonLib свойство `SolutionName` имеет значение `CommonLib`. Поэтому проекты импортируют `CommonLib.Build.props` и `CommonLib.Build.targets` из корня репозитория. Эти файлы содержат настройки именно решения CommonLib.
- При подключении проектов как исходников или Git-субмодуля в другое решение значение `SolutionName` должно соответствовать решению-потребителю, например `MyProduct`. Тогда проекты ищут `MyProduct.Build.props` и `MyProduct.Build.targets` в каталоге CommonLib. Файлы `CommonLib.Build.*` не импортируются.

**При подключении CommonLib к другому решению потребитель должен самостоятельно предоставить необходимые общие настройки MSBuild.** Для этого можно использовать стандартные `Directory.Build.props` и `Directory.Build.targets` в каталоге решения-потребителя (или в подходящем общем каталоге выше проектов в дереве каталогов).

Важно учитывать порядок импорта MSBuild:

- `Directory.Build.props` автоматически импортируется до обработки содержимого проекта. В нём необходимо задать `SolutionName` и другие свойства, которые должны быть доступны явным импортам в проектах CommonLib.
- `Directory.Build.targets` автоматически импортируется после обработки содержимого проекта. В нём размещают общие цели и настройки, которые должны применяться на позднем этапе сборки. Задавать в нём `SolutionName` для импорта `$(SolutionName).Build.props` уже поздно.

Оба файла должны содержать настройки, необходимые конкретному решению и используемым библиотекам; их содержимое не копируется из CommonLib автоматически. MSBuild ищет эти файлы вверх от каталога каждого проекта. Если ближе к проекту находится вложенный файл с таким же стандартным именем, он может заменить файл, расположенный выше по дереву.

Для проектов nanoCAD дополнительно используется `Shared.NC.props`. Он задаёт общие параметры CAD-сборок и генерирует префикс команд из имени решения:

- для решения `drzTools` префикс совпадает с именем решения;
- для остальных решений используется формат `drz_$(SolutionName)`.

### Источники NuGet

В корневом `NuGet.config` объявлены источники:

- `nuget.org` — публичные пакеты;
- `nanoDev` — пакеты nanoCAD;
- `CommonLibLocal` — локальный каталог `Nuget` в корне репозитория.

При использовании CommonLib как Git-субмодуля конфигурацию NuGet необходимо учитывать отдельно: наличие `NuGet.config` внутри субмодуля не гарантирует, что NuGet применит его при восстановлении пакетов основного решения.

**В `NuGet.config` корневого решения-потребителя необходимо явно добавить локальный источник, указывающий на каталог `Nuget` внутри субмодуля CommonLib.** Путь к источнику задаётся относительно расположения самого `NuGet.config`. Например, если субмодуль находится в каталоге `CommonLib` рядом с конфигурацией решения:

```xml
<packageSources>
  <add key="CommonLibLocal" value="./CommonLib/Nuget" />
</packageSources>
```

Если субмодуль размещён в другом каталоге, укажи соответствующий относительный путь. Это позволяет использовать локальные пакеты CommonLib независимо от абсолютного расположения репозитория на компьютере разработчика.
